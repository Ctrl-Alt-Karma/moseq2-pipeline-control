# R5 packet integrity

R5 is a new operator-packet identity created for a single provenance role
correction. It does not rewrite R3 or R4.

`SHA256SUMS.txt` (R2), `SHA256SUMS_R3.txt` and `SHA256SUMS_R4.txt` are preserved
unchanged as historical evidence. The earlier manifests no longer verify clean
against this packet, which is expected: the changed governed members are
`08_run_r1_full_session_validation.sh` and
`helpers/verify_r1_full_session_provenance.py`. The R4 packet identity remains
verifiable at operator commit `f026298a0cf2a0fa97bedb29245424bddcf0713b`.

R5 uses `SHA256SUMS_R5.txt`, generated by `helpers/build_r5_packet_manifest.py`
in deterministic path order, covering every regular packet member except
`SHA256SUMS_R5.txt` itself.

## Why R5 exists

The runtime PCA binding treated the frozen **training-score** artifact as if it
were the PCA **component basis**:

- component basis: `pca/pca.h5`, SHA-256
  `6b587854412c1b0a0b69759f4262e4fac3583b1aa6144093fcd3d2bf1ff0b368`,
  containing `/components` (25, 6400) float32
- training scores: `pca/pca_scores.h5`, SHA-256
  `26e30500be1e885422307c707e0b7b5ec619c70149d557a764d3daa475108912`,
  containing `metadata`, `scores`, `scores_idx` and **no** `/components`

`moseq2-pca apply-pca` reads `/components`, so binding the score artifact
aborted stage 03 after extraction had already run. A hash-only gate could not
distinguish the two files: the score artifact hashed exactly as bound.

R5 therefore (a) binds the component basis at runtime and (b) adds one semantic
role check — the runtime PCA artifact must be readable HDF5 containing
`/components` with shape (25, 6400) and dtype float32 — which fails closed
before candidate science.

The training-score artifact is **not** deleted or redefined. It remains frozen
upstream evidence for the production model and the Tier-B envelopes. It is not
the runtime input to apply-pca.

No PCA refit, model refit, scientific retuning, new PCA selection, or change to
Tier-B/Tier-C criteria is involved. Raw inputs, roster positions, config,
classifier, production model and all other scientific identities are unchanged.

## Companion PCA yaml dependency

`moseq2-pca` derives the companion PCA yaml as `splitext(pca_file)[0] + ".yaml"`
and `get_pca_yaml_data` raises `OSError` if it is absent. That companion carries
the frozen filter and mask parameters actually consumed at apply time, so it is a
consumed scientific dependency rather than incidental metadata.

The operator therefore binds
`pca/pca.yaml`, SHA-256
`ba47df9b1229ab6dae884adf2fab49cfde4a07c5d44575e35547be12277af0d9`, 2714 bytes,
requires it to exist, and verifies its path, hash and byte count in the
provenance preflight, failing closed before science on any mismatch.

Stage 03 is invoked with the original verified PCA path rather than the run-local
copy, so the locked pipeline resolves the genuine companion. The immutable
evidence copy `inputs/pca_components.h5` is still written, and no PCA yaml is
copied into the run output tree.
