# R4 packet integrity

R4 is a new operator-packet identity created for a single pre-science
compatibility defect. It does not rewrite R3.

`SHA256SUMS.txt` (R2) and `SHA256SUMS_R3.txt` are both preserved unchanged as
historical evidence. `SHA256SUMS_R3.txt` no longer verifies clean against this
packet, and that is expected: it reports 56 / 58 because two governed members
changed, `helpers/record_r1_raw_frame_accounting.py` (the defect itself) and
`tests/test_r1_full_session_operator_gate.sh` (its fixture switched to the
list form, plus the new raw-frame-accounting traversal assertion). No other
governed member differs. The historical R3 packet identity
remains verifiable at operator commit `59b15ce796bdda2b1d534fc34cded3e877360cac`
and in the untouched R3 checkout, which still verifies 58 / 58.

R4 uses `SHA256SUMS_R4.txt`, generated by `helpers/build_r4_packet_manifest.py`
in deterministic path order, covering every regular packet member except
`SHA256SUMS_R4.txt` itself.

## Why R4 exists

`record_r1_raw_frame_accounting.py` assumed the acquisition metadata field
`DepthResolution` was always a string of the form `"512x424"`. The staged R1
sessions declare it as a two-element integer list, `[512, 424]`. A non-empty
list is truthy, so `resolution or ""` passed the list into `re.match`, which
raised `TypeError` and aborted the operator before science with
`RAW_FRAME_ACCOUNTING_FAILED`. R3's synthetic fixture used the string form, so
its gate never exercised the list form; the Tier-E negative control failed one
step earlier at the provenance preflight and never reached this code.

R4 adds list-form support, keeps string-form behaviour, and makes every other
representation fail closed through the accounting receipt instead of raising.
No scientific setting, threshold, roster, model, PCA, config, classifier or
tolerance is changed, and no raw data is altered.
